     План: экспорт 12 иконок из набора в drawable с прозрачным фоном

     Context

     У пользователя есть растровый набор /home/kr0fff/Downloads/icons.png
     (1024×1024, RGB) — 12 золотых art-deco иконок на белом фоне, разложенных
     сеткой 3 строки × 4 столбца. Нужно нарезать каждую иконку в отдельный PNG
     так, чтобы крой не задевал соседние иконки, сделать белый фон прозрачным и
     положить результат в Compose-ресурсы проекта, чтобы их можно было
     использовать через Res.drawable.*.

     Сегментация уже проверена (read-only прогон проекций по осям): белые
     «канавки» между иконками дают ровно 12 чистых bounding-box'ов, ни один не
     пересекается с соседями.

     Решения (подтверждены пользователем)

     - Имена: описательные, lowercase snake_case (валидно для Compose
     Resources).
     - Прозрачность: глобальный white-key — весь белый (фон И белые промежутки
     внутри иконок) → прозрачный.
     - Холст: единый квадратный прозрачный холст для всех 12, иконки
     отцентрованы, без изменения относительного масштаба.
     - Формат: PNG RGBA (исходник растровый, вектор не уместен).

     Целевая папка

     composeApp/src/commonMain/composeResources/drawable/
     (там уже лежит compose-multiplatform.xml — его не трогаем). После
     добавления PNG Gradle-синк сгенерирует аксессоры Res.drawable.ic_*.

     Сетка и имена (строки сверху-вниз, столбцы слева-направо)

     Детектированные bounding-box'ы (row-band y → column-bands x):

     Строка 1 (y 224–371):
     1. ic_medallion.png   — монета/медальон с буквой «S» и лучами  (x 157–280)

● Now I can explain it precisely.

  Что делает StorageInitProvider и зачем

  EncryptedSharedPreferences (и вообще SharedPreferences) на Android требует
  Context. А StorageHelper сделан как no-arg object (вы просили «объект
  StorageHelper») — у синглтона-объекта нет способа самому достать Context.

  StorageInitProvider — это пустой ContentProvider, который Android сам 
  инстанцирует на самом раннем старте процесса (до Application.onCreate), и в
  его onCreate мы просто сохраняем applicationContext в холдер. Регистрация в
  манифесте — единственный способ сказать фреймворку «создай этот провайдер».
  Данных он не хранит, это чистый трюк захвата контекста.

  Это не самодельная экзотика — ровно так работают Firebase, WorkManager,
  LeakCanary и сам androidx App Startup.더 того: multiplatform-settings-no-arg,
  который у вас в зависимостях, под капотом делает то же самое (мержит свой
  ContentProvider/Startup-инициализатор), просто прячет это от вас.

  Почему не через Koin

  Два момента:
  1. Koin в проекте не инициализирован — startKoin нигде не вызывается (мы это
  сознательно откладывали в задачах навигации/хранилища, чтобы не трогать точки
  входа обеих платформ).
  2. Koin сам по себе проблему контекста не решает — вам всё равно нужно
  скормить Android Context в Koin через startKoin { androidContext(...) }, а это

     План: перевести StorageHelper на Koin DI (убрать ContentProvider)

     Context

     В StorageHelper Android-контекст для EncryptedSharedPreferences сейчас
     добывается через StorageInitProvider (пустой ContentProvider,
     зарегистрированный в манифесте) — рабочий, но «магический» паттерн.
     Пользователь предпочёл правильный DI. Koin уже в зависимостях
     (koin-core/-compose/-compose-viewmodel в commonMain, koin-android в
     androidMain), но startKoin нигде не вызывается. Переводим хранилище на
     Koin: инициализируем Koin в обеих точках входа, Context берём через
     androidContext(), StorageInitProvider и запись в манифесте удаляем.

     Решение (подтверждено пользователем: «Koin (правильный DI)»)

     Абстрагируем создание Settings за SettingsFactory, которую отдаёт
     платформенный Koin-модуль; StorageHelper становится классом-синглтоном из
     Koin (сохраняя весь текущий API и ленивую схему двух хранилищ).

     Изменения

     commonMain

     - storage/StorageHelper.kt:
       - fun interface SettingsFactory { fun create(encrypted: Boolean): 
     Settings }.
       - object StorageHelper → class StorageHelper(private val factory: 
     SettingsFactory); plainSettings/encryptedSettings = by lazy { 
     factory.create(...) }. Весь публичный API (put/get/…OrNull,
     putObject/getObject, remove/clear/contains) сохраняется как методы
     экземпляра.
       - Удалить internal expect fun createSettings(encrypted).
     - di/Koin.kt (новый):
       - expect fun platformStorageModule(): Module — отдаёт SettingsFactory.
       - val storageModule = module { single { StorageHelper(get()) } }.
       - fun initKoin(appDeclaration: KoinAppDeclaration = {}) { if 
     (GlobalContext.getOrNull() == null) startKoin { appDeclaration(); 
     modules(platformStorageModule(), storageModule) } } (guard от двойного
     старта).

     androidMain

     - di/Koin.android.kt (новый): actual fun platformStorageModule() = module {
     single<SettingsFactory> { val ctx = androidContext(); SettingsFactory { 
     encrypted -> ...EncryptedSharedPreferences(MasterKey AES256-GCM) либо 
     getSharedPreferences..., обёрнутые в SharedPreferencesSettings } } } —
     переносит сюда логику из старого StorageHelper.android.kt.
     - MainApplication.kt (новый): class MainApplication : Application() { 
     override fun onCreate() { super.onCreate(); initKoin { 
     androidContext(this@MainApplication) } } }.
     - Удалить storage/StorageHelper.android.kt (ContentProvider +
     AppContextHolder + createSettings).
     - AndroidManifest.xml: убрать <provider …StorageInitProvider …>; добавить в
     <application> атрибут
     android:name="com.trid.test.kmpsample.MainApplication" (FQN — rebundle

     iosMain

     single<SettingsFactory> { SettingsFactory { encrypted -> if (encrypted)
